# 检查清单与验证记录

说“通过”的时候，要说清楚是哪一步通过了。模板能解析、面板健康、节点能连、真客户端能用、设备不漏 IP，这是五个不同的结果，一个不能顶替另一个。

## 实机验证（2026-11-18）

在一台被授权测试的 KVM VPS 上实际换了两轮系统。第一轮确认部署和恢复能用，第二轮用修好以后的代码重新装 Ubuntu 24.04 x86_64。部署前通过服务商核对了新的 SSH 公钥、新的 boot ID、系统模板和公网 IP，也确认了旧的配置目录已经不在。部署用的是这一轮的仓库代码，报告里记的源码摘要和本机一致。

| 检查 | 结果 |
| --- | --- |
| 仓库与镜像 | 本机 125 项测试通过，Compose 和文档链接检查通过。实机核对 S-UI v1.6.6 固定镜像及其内置 sing-box 1.14.4。 |
| VLESS Reality | sing-box 1.14.4 单节点测试通过。HTTPS 200、VPS 出口匹配、错误 UUID 无法访问，恢复正确 UUID 后再次成功。 |
| VLESS TLS | 单节点测试通过。可信证书校验、HTTPS 200、VPS 出口匹配、错误 UUID 拒绝、恢复正确凭据后重新连接。 |
| AnyTLS | 单节点测试通过。可信证书校验、HTTPS 200、VPS 出口匹配、错误密码拒绝、恢复正确凭据后重新连接。 |
| Surge Mac 6.5.0（10960） | AnyTLS 正确凭据测试及恢复测试均返回 HTTPS 200，出口匹配。错误凭据返回 EOF，Surge 未明确给出拒绝原因。 |
| HTTPS 管理入口 | S-UI 公网登录与会话通过。CLIProxyAPI v8.0.76 管理页、管理 Key 和 API Key 鉴权通过。没有配置上游，模型调用、流式响应和 WebSocket 未测试。 |
| 订阅与流量 | 两种新链接返回对应配置，轮换后旧链接均返回 404。已从官方 API 拉取额度、用量及重置时间。客户端定时刷新和流量显示仍待实测。 |
| 生命周期 | 第一轮实际备份恢复后，服务和三节点复测通过。第二轮重复部署保留凭据，S-UI 容器重建后继续使用原账号和节点，续期演练、正式证书同步和加载、备份检查通过。自然到期触发的续签和跨版本回滚未测试。 |
| 其余客户端与隐私 | 未实测 v2rayN、v2rayNG、UDP 转发、TUN、DNS、IPv6、WebRTC、断线与切网。 |

实测中修了这几处：用官方 API 读新主机的公钥；给 Surge 的临时 AnyTLS 配置补上策略名称；本机 Python 没有根证书时，加载固定版本的证书包。第二轮测三个节点时，用的是核对过发布摘要的原生 macOS 版 sing-box，证书验证一直开着。

## 第三轮：Clash 订阅、IPv4 出口和规则镜像（2026-11-18）

还是同一台被授权的 KVM VPS，通过服务商 API 换成 Ubuntu 24.04 x86_64 后，用仓库入口部署。旧数据由机器的主人明确放弃了（`--discard-existing-data`）。第一次 `deploy` 碰上系统首次启动时 `apt-get` 占着锁，停了下来；改成等软件包锁释放以后，在同一个新系统上重跑通过。

| 检查 | 结果 |
| --- | --- |
| 仓库 | 本机 137 项测试通过；Compose 解析通过；固定 Mihomo 1.19.33 解析生成的 Clash 配置通过；S-UI v1.6.6 实际 API 集成测试通过（含 IPv4 出口配置读回）。 |
| 服务检查 | `verify` 18 项通过，新增规则镜像下载与错误令牌 404、规则刷新定时器、核心配置只解析 IPv4 并拒绝 IPv6 目标。 |
| 三个节点 | sing-box 1.14.4 单节点测试通过：HTTPS 200、出口匹配、错误凭据拒绝、恢复后重连。经节点访问 IPv6-only 站点和 IPv6 字面地址都失败。**这台 VPS 本身没有公网 IPv6**，所以这一项在这里必然失败，不能单独证明拒绝规则生效；规则本身由核心配置读回确认。 |

## 第四轮：Shadowrocket 订阅、微信 / Play 规则、Reality 回落本机、证书复用（2026-11-18）

还是同一台被授权的 KVM VPS，前后两次通过服务商 API 换成 Ubuntu 24.04 x86_64，都用仓库入口部署，旧数据由机器的主人明确放弃。

1. 第一次换系统后，部署在申请 IP 证书时被 Let's Encrypt 拒绝：同一 IP 一周内只能签 5 张，之前几轮换系统已经用完。等额度恢复后在同一系统上重跑通过。
2. 为了避免以后再撞上这个限制，加了"换系统前保存证书、换系统后复用"。随后第二次换系统实测：`reinstall` 先保存了证书，`deploy` 在 cert 阶段复用了这张证书，没有申请新证书。

| 检查 | 结果 |
| --- | --- |
| 仓库 | 本机 142 项测试通过（12 项因未设环境变量跳过）。加 `VALIDATE_CORE` 和 S-UI / 节点 / CLIProxyAPI 集成测试后 142 项通过（7 项跳过）。Compose 解析通过。Reality 回落本机经固定 sing-box 1.14.4 与 Mihomo 1.19.33 客户端认证通过。 |
| 服务检查 | 两次部署后 `verify` 都是 19 项通过。新增的 `reality_self_fallback` 确认：不带 Reality 凭据直接连 443 时，看到的是服务器自己的 IP 证书。 |
| 证书复用 | 第二次换系统后，部署日志显示"复用换系统前保存的 IP 证书"，`certificate_pair` 与 `trusted_certificate_loaded` 通过。 |
| 三个节点 | 两次部署后，sing-box 1.14.4 单节点测试都通过。IPv6 目标被拒绝（这台 VPS 本身没有公网 IPv6，限制同第三轮）。 |
| Clash 订阅 | 固定 Mihomo 1.19.33 加载真实订阅：从服务器镜像下载 GeoSite、IP 库和 ASN 库，HTTPS 请求成功，出口为 VPS。 |
| Shadowrocket 订阅 | 返回 200，带用量头，解码后是两个 VLESS 加一个 AnyTLS 节点。 |
| 未测试 | Shadowrocket、Clash Verge Rev、OpenClash 真机；Xray 内核连 Reality 回落本机的节点；微信、Google Play 规则在真实设备上的效果；DNS、WebRTC 泄露。 |

## 历史记录

2026-10-26 的旧版做过 Python 模板检查、Compose 解析、用固定的 sing-box 1.14.4 检查示例，以及 S-UI v1.6.6 的隔离启动和健康检查。**当时用的协议组合和现在不一样，这些记录证明不了现在的三个节点或自动部署能用。** 单独校验镜像里的 sing-box 版本，也不代表 S-UI 实际内置的就是这个版本。

后来新加的 VLESS Reality / VLESS TLS / AnyTLS 自动部署、可信的 HTTPS 面板和订阅、CLIProxyAPI、本机账号页、换系统后部署，每一项都要单独存新的检查结果。判断依据是仓库测试的实际输出和私有的部署记录。真实 VPS、客户端和生命周期这些项目没做完之前，下面对应的复选框就空着。

## 本轮本机隔离验证（2026-11-17）

在本机的隔离环境里，用固定版本的 sing-box 给三个节点各发了一次代理请求，也各测了一次错误凭据被拒。通过 S-UI 的实际 API 完成了配置，检查了重跑不会改坏东西、重启后配置还在。这说明配置和 API 在本机环境里能用，但代替不了公网证书、真实 VPS、客户端和防泄露的结果，这些当时都还没测。这一轮完整跑了 94 项测试，全部通过，没有跳过；Compose 解析、文档相对链接和 diff 检查也通过了。另外还验证了固定版本 CLIProxyAPI 程序在本机容器里的鉴权、密码接入时的数据通道、恢复流程和失败回滚。恢复测试用的是隔离的文件目录和模拟的服务控制，代替不了在 VPS 上真的停机恢复一次。

## 1. 本机检查

```sh
python3 -m unittest discover -s tests -v
docker compose -f deploy/compose.yaml config --quiet
VALIDATE_CORE=1 python3 -m unittest discover -s tests -v
VALIDATE_CORE=1 RUN_PANEL_INTEGRATION=1 RUN_PANEL_NETWORK=1 \
RUN_PROBE_INTEGRATION=1 RUN_CLIPROXY_INTEGRATION=1 \
python3 -m unittest discover -s tests -v
```

第一条检查模板和自动化逻辑。第二条只解析 Compose。第三条需要 Docker 和 OpenSSL，用固定版本的 sing-box 和 Mihomo 检查配置；如果跳过了或者 Docker 用不了，要写明没做完，不能算通过。

- [x] 三个节点与客户端一一对应，凭据占位符配对，两个 VLESS 节点没有被同类型合并。
- [x] 镜像固定 tag 与摘要，无真实地址、令牌、私钥进入可提交文件。
- [x] Markdown 相对链接可用。
- [x] HTML 转义正确，不请求 CDN、统计或第三方二维码接口。
- [x] 核心分别接受三个入站及客户端；另记录 S-UI 实际内置核心版本。

## 2. 服务检查

在本机运行 `python3 scripts/vps.py --state private/target.json verify`，再对照实际结果，把它没自动检查到的项目补查一遍。

- [ ] SSH 密钥和实际端口可用；系统、架构、目标 IP 已核对。
- [ ] 2095/2096、CLIProxyAPI 等后端仅回环监听，从外部不能直接访问。
- [ ] Nginx 的 TCP 9443 使用可信证书；公网面板要求新的随机管理员认证。
- [ ] TCP 443、2443、8443、9443、9444 和证书校验所需 TCP 80 正确放行；保留 SSH；未默认开放 UDP 443。
- [ ] 数据库持久化、目录与密钥权限正确，镜像摘要匹配。
- [ ] 三个 S-UI 入站、TLS、用户关联与发布地址正确，实际核心运行。
- [ ] 每种订阅返回正确格式；错误令牌和未知路径不返回私人配置；访问日志不记录秘密 URL。
- [ ] CLIProxyAPI 管理认证、调用认证、流式响应和 WebSocket 按实际功能检查。初始无上游账号时，不能把“无模型可调用”标成上游调用成功。
- [ ] 搬瓦工流量来自该实例官方 API；失败时明确显示不可用或缓存时间，未使用固定流量冒充官方数据。
- [ ] 没有搬瓦工 API 时，本机网卡统计按配置的额度、重置日和计费方式显示，重启后继续累加，校准后数值正确。
- [ ] Clash 规则数据已镜像到服务器；只能用 Clash 令牌下载，错误令牌返回 404；校验失败时保留上一份。
- [ ] 实际运行的核心配置只解析 IPv4、拒绝 IPv6 目标。

## 3. 节点与真实客户端

在你自己的电脑上运行下面的命令，用固定版本的 sing-box 一个个节点地测 HTTPS、出口 IP、错误凭据会不会被拒、断开后能不能重连。结果存在 `private/network.json`，代替不了 Surge、v2rayN 或 v2rayNG 的真机测试。导出账号页时，报告要跟当前的节点和服务器版本指纹对得上，旧部署或旧凭据的结果不会再显示通过。

```sh
python3 scripts/vps.py --state private/target.json network
python3 scripts/vps.py --state private/target.json export
```

- [ ] Reality 443：认证、受控 HTTPS 请求、出口地址符合预期。
- [ ] VLESS TLS 2443：证书验证开启，身份、有效期和完整链正确，请求成功。
- [ ] AnyTLS 8443：证书验证开启，请求成功。
- [ ] 各节点错误凭据被拒绝，每条单独测试，没有自动切换掩盖失败。
- [ ] 经每个节点访问只有 IPv6 的站点和 IPv6 字面地址都失败，IPv4 出口仍匹配服务器。
- [ ] 需要的 UDP 转发逐项测试；没有 UDP 入站监听不代表 UDP 应用一定不能转发。
- [ ] Surge AnyTLS：记录系统、应用版本、实际连接结果。
- [ ] v2rayN 和 v2rayNG VLESS：分别记录系统、应用、核心版本与结果。
- [ ] Shadowrocket：记录系统、应用版本，三个节点分别连接的结果（含 AnyTLS）。
- [ ] Reality 回落到本机：不带凭据连 443 看到本机 IP 证书；sing-box、Mihomo、Xray 客户端分别能认证。
- [ ] Clash 订阅由固定 Mihomo 核心解析通过；Clash Verge Rev / OpenClash 真机导入后，三个节点、AUTO 切换、规则分流分别记录版本与结果。

没有 Windows 或 Android 设备，就把对应的客户端写成“未测试”。别的设备或别的内核测通了，不能顶替它。

## 4. IP 防泄露

照 [详细方法](leak-protection.md) 做，每个客户端分开记：

- [ ] 指定代理与允许直连的范围已明确，私有保存本地公网地址作对照。
- [ ] TUN/VPN 路由覆盖预期应用；受保护 IPv4/IPv6 按预期代理或被阻断。
- [ ] DNS 没有意外回落到本地网络；WebRTC 没暴露本地公网 IP。
- [ ] 节点故障、客户端退出时，受保护流量不会自动直连。
- [ ] 切网、休眠唤醒、设备重启后重复上述检查。

## 5. 维护与从零复验

- [ ] 容器重建后用户、TLS、入站仍保留；部署重跑不会变更有效凭据。
- [ ] 备份能在独立测试位置恢复；更新与回滚已演练并记录摘要。
- [ ] 证书 `renew --dry-run`、正式证书同步、服务实际加载分别检查；失败保留旧证书。
- [ ] 订阅自动刷新与令牌轮换已检查；新订阅与本机 HTML 一致。
- [ ] 所有修正写入仓库后，在明确获授权的测试目标上真正换一次系统，再从仓库入口部署复验。

完整地址、凭据、账号页和原始日志只存在 `private/` 或服务器上权限受限的目录里。公开的记录只写日期、仓库提交、版本、方法和每一项的结果，别用一个总的“通过”把没测的项目也盖过去。
